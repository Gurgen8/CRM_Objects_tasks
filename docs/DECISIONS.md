# Решения и допущения

## Где ТЗ допускало разные трактовки

1. **Роль одна на пользователя.** Пользователь либо постановщик, либо исполнитель. Роль хранится в `app_metadata` (меняет только администратор) и копируется в `profiles.role` триггером.
2. **Исполнитель обязателен при создании задачи.** Без исполнителя задача застряла бы в «Новой»: взять её в работу может только назначенный исполнитель. Назначить можно только пользователя с ролью «Исполнитель», это проверяет база.
3. **Все постановщики равноправны.** «Видит всё» трактую так: любой постановщик может редактировать, удалять и принимать любые задачи, не только свои.
4. **Постановщик может сменить исполнителя в любом статусе.** Новый исполнитель продолжает с текущего статуса. Прежний исполнитель сразу теряет доступ к задаче. Смена исполнителя в историю не пишется: по ТЗ история — это смены статусов.
5. **Постановщик не выполняет действия исполнителя.** «Взять в работу» и «Отправить на проверку» может только назначенный исполнитель, как в таблице переходов ТЗ.
6. **Комментарий можно оставить при любой смене статуса.** Обязателен он только при возврате на доработку. Комментарий из одних пробелов считается пустым.
7. **Статус «Принята» — финальный.** Переходов из него нет. Если работу нужно переделать, ставится новая задача.
8. **Задачу создаёт только постановщик, и всегда в статусе «Новая».** Первая запись истории («— → Новая») появляется автоматически.
9. **Удаление.**
   - Задачу постановщик удаляет вместе с её историей. Удалить историю отдельно от задачи нельзя никому.
   - Объект, в котором есть задачи, удалить нельзя: сначала нужно разобраться с задачами. Так мы защищаемся от случайной потери данных по целой стройке.
10. **Исполнитель видит в карточке объекта только свои задачи** на этом объекте, а не все задачи объекта: «видит только свои задачи».
11. **Видимость профилей.** Постановщик видит всех пользователей, ведь ему нужно выбирать исполнителя. Исполнитель видит себя и тех, кто фигурирует в его задачах (автор задачи, участники истории), а полный список сотрудников — нет.
12. **Чужая задача выглядит как несуществующая.** На попытку открыть или перевести чужую задачу исполнитель получает «не найдена», а не «нет прав», чтобы не узнавать даже о её существовании.

## Технические решения

- **Без отдельного бэкенда.** Логика переходов и права доступа живут в Postgres: RLS, функции, триггеры. Отдельный сервер был бы лишним звеном, которое тоже нужно защищать, а правила в базе обойти нельзя.
- **Два слоя прав.**
  - `GRANT` по колонкам: через API в принципе нельзя записать `status`, `created_by`, `created_at`, а в историю нельзя писать вообще.
  - RLS по строкам: кто какие записи видит и меняет.
  
  Триггеры дублируют критичные проверки на случай ошибки в правах.
- **Смена статуса только через функцию `change_task_status`.** Она в одной транзакции блокирует строку (защита от гонки двух одновременных нажатий), проверяет право на переход и комментарий, меняет статус и пишет историю. Автор записи и время берутся из сессии и часов сервера, клиент их передать не может.
- **Правила переходов хранятся в таблице `task_status_transitions`**, а не зашиты в код. Ими пользуются и проверка в базе, и интерфейс: кнопки на экране строятся функцией `get_available_transitions`. Поэтому интерфейс и база не могут разойтись.
- **Служебные функции лежат в схеме `private`**, которую Supabase не публикует через API.
- **Демо-данные создаются от имени пользователей через обычный API**, а не прямыми вставками в базу. Поэтому история в демо настоящая, а сам seed заодно проверяет рабочий сценарий целиком.
- **Проверка безопасности автоматизирована** (`npm run test:security`): 33 попытки обхода от имени анонима, исполнителя и постановщика.
- **Типы TypeScript генерируются из схемы БД.** Если поменять базу и не обновить фронтенд, сборка упадёт.

## Что не успел или сознательно не делал

- **Автотесты интерфейса в репозитории.** Ключевые сценарии проверены вручную в браузере за обе роли, но автоматического прогона интерфейса в проекте нет. Защиту данных проверяет `test:security`.
- **CI** (GitHub Actions с прогоном миграций и `test:security` на каждый коммит). Следующий очевидный шаг.
- **Журнал изменений полей задачи** (кто поменял исполнителя или описание). Сейчас в истории только статусы, как в ТЗ.
- **Поиск, фильтры и пагинация** в списках. Для объёма тестового не нужны, при росте данных понадобятся.
- **Уведомления** исполнителю о новой задаче и постановщику о задаче на проверке (email или Telegram).
- **Управление пользователями из интерфейса.** Сейчас пользователей создаёт администратор через Supabase.
- **Восстановление пароля.** При закрытой регистрации пароль выдаёт и сбрасывает администратор.
